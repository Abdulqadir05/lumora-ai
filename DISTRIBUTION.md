# Lumora AI — Private Distribution Guide

This guide covers private distribution of Lumora AI on Android and iOS. Nothing is published to Google Play, and nothing is released publicly on the App Store.

| Channel | Platform | EAS profile | Output | Who can install |
| --- | --- | --- | --- | --- |
| **Signed APK** | Android | `android-apk` | Release-signed `.apk` (EAS internal distribution) | Anyone with the link or file |
| **TestFlight** | iOS | `testflight` | App Store–signed `.ipa` uploaded to App Store Connect | Internal team (≤100) and external testers (≤10,000) via email or public link |
| **Ad hoc** | iOS | `ios-adhoc` | Ad hoc–signed `.ipa` | Only iPhones/iPads whose UDIDs are registered (≤100 per device type per membership year) |

All three profiles extend `base` in `eas.json`. That means the **same backend URL**, the **same EAS environment** (`production`, which holds the client token), Node 22.17.0 and pnpm 10.34.3. All profiles also use the **same bundle identifier**, defined once in `app.json`. No profile overrides it, and the release guard plus the tests enforce this.

> **Build status rule:** a build counts as successful only when EAS reports `finished`. Check with `eas build:list --limit 1` or the build page. Nothing in this repository has been built on EAS yet; no Expo, Apple or Google accounts were used in preparing it.

## 1. Required accounts and credentials

| Credential | Needed for | Where to get it | Stored where |
| --- | --- | --- | --- |
| **Expo account** | All builds | expo.dev, then `eas login` | Your machine (`~/.expo`). For CI, use an `EXPO_TOKEN` (Account settings → Access tokens) |
| **Apple Developer Program** membership (individual or organization, paid yearly) | TestFlight **and** ad hoc | developer.apple.com/programs | — |
| Apple account role **Account Holder or Admin** (or App Manager with access to Certificates, Identifiers & Profiles) | Lets EAS create the distribution certificate, provisioning profiles and device registrations | App Store Connect → Users and Access | — |
| **App Store Connect API key** (Team key, role **App Manager**): Key ID, Issuer ID, `.p8` file | `eas submit` (non-interactive) and `scripts/testflight.mjs` | App Store Connect → Users and Access → Integrations → App Store Connect API | `.p8` on your machine **outside git** (`*.p8` is gitignored), or uploaded to EAS via `eas credentials -p ios` |
| **Android release keystore** | Signing the APK | Generated by EAS on the first Android build | EAS servers. **Download a backup** (§3.5) |
| **Lumora backend URL** (HTTPS) | Every build | Your deployed `lumora/backend` | `eas.json` → `build.base.env.EXPO_PUBLIC_LUMORA_API_URL` |
| **Lumora client token** | Every build | `openssl rand -hex 32`, then add it to the backend's `LUMORA_CLIENT_TOKENS` | EAS environment variable `EXPO_PUBLIC_LUMORA_CLIENT_TOKEN` (environment `production`) |

**Never in the mobile app:** `LLM_API_KEY`, `GROQ_API_KEY`, `OPENAI_API_KEY`, `GEMINI_API_KEY`, `TAVILY_API_KEY`, `COINGECKO_DEMO_API_KEY` and `LUMORA_CLIENT_TOKENS`. These live only in `lumora/backend/.env` or your hosting provider. `scripts/check-release-env.mjs` runs automatically on EAS through the `eas-build-pre-install` hook. It fails the build if any of these appear, if a secret-like `EXPO_PUBLIC_*` variable exists, if the backend URL isn't `https://`, or if the bundle identifier changes.

A Google Play developer account is **not** needed.

## 2. One-time project setup

```bash
npm install -g eas-cli@latest          # eas.json requires >= 16
eas login
cd lumora/mobile
corepack enable && pnpm install --frozen-lockfile
```

1. **Application identifiers:** the confirmed Android package is `ai.lumora.app` in `app.json` and `CANONICAL_IDS.android`. Choose an iOS bundle identifier separately before iOS distribution; iOS build profiles remain blocked while its current value is a placeholder.
   - `scripts/check-release-env.mjs` → `CANONICAL_IDS` (platform-specific values must match `app.json`)
2. **Set the backend URL once** in `eas.json` → `build.base.env.EXPO_PUBLIC_LUMORA_API_URL` (must be `https://`).
3. **Link the EAS project** (writes `extra.eas.projectId` and `owner` to `app.json`; commit the change):
   ```bash
   eas init
   ```
4. **Current client-token setup:** the existing EAS profiles expect a shared client token in the EAS `production` environment:
   ```bash
   eas env:set --environment production --name EXPO_PUBLIC_LUMORA_CLIENT_TOKEN --value "<token>" --visibility sensitive
   eas env:list --environment production
   ```
   `EXPO_PUBLIC_*` values are compiled into the app, so the shared token can be extracted from an APK. This static-token setup is not suitable for public distribution; implement user authentication and usage quotas before sharing the APK publicly. `sensitive` masks the value in build logs.
5. **Verify locally** before spending build minutes:
   ```bash
   pnpm verify:release        # guard for all three profiles
   pnpm test:distribution     # eas.json/app.json invariants, branding, TestFlight tooling
   pnpm typecheck && pnpm test && pnpm doctor
   ```

## 3. Android: signed release APK (no Play Store)

### 3.1 Build
```bash
pnpm build:android:apk        # = eas build --platform android --profile android-apk
```
On the first run, answer **Yes** to *"Generate a new Android Keystore?"*. EAS creates the release keystore, runs `:app:assembleRelease` and signs the APK with it. `autoIncrement` raises `versionCode` on every build, so new APKs install over old ones.

### 3.2 Confirm success
Wait until EAS prints **Build finished**, then:
```bash
eas build:list --platform android --build-profile android-apk --limit 1
```
Proceed only if the status is `finished`. If it's `errored`, open the build page link for logs.

### 3.3 Share
Choose any of these:
- **EAS install page:** send the build page URL. Opening it on an Android phone shows an **Install** button, and there's a QR code for desktop viewers.
- **Direct APK file:** `eas build:view <BUILD_ID> --json` prints `artifacts.buildUrl`, a direct `.apk` download. Share that link or the downloaded file (email, Drive, messaging, MDM).

### 3.4 Install (tester instructions)
1. Open the link or file on the Android device and download the APK.
2. When prompted, allow **Install unknown apps** for the browser or Files app (Settings → Apps → Special app access → Install unknown apps).
3. Tap **Install**. If Google Play Protect warns about an unknown developer, choose **More details → Install anyway**.
4. To update, install the newer APK over the old one. It must be signed with the **same keystore**, which EAS ensures.

Requirements: Android 7.0+ (minSdk 24, from the generated Android project). Updates require the same signing key and a higher `versionCode`.

### 3.5 Back up the keystore
```bash
eas credentials -p android     # select android-apk → Keystore → Download existing keystore
```
Store the `.jks` file and passwords in a password manager. Without this keystore, future APKs can't update installed copies.

Optional signature check: `apksigner verify --print-certs lumora.apk`. Its SHA-256 should match the fingerprint shown by `eas credentials -p android`.

## 4. iOS method A: TestFlight

### 4.1 Build (App Store distribution signing)
```bash
pnpm build:ios:testflight      # = eas build --platform ios --profile testflight
```
Sign in with your Apple account when asked (or let EAS use the stored API key). EAS creates or reuses the **Apple Distribution certificate** and an **App Store provisioning profile** for the bundle identifier. `ITSAppUsesNonExemptEncryption=false` is preset, so TestFlight won't ask the export-compliance question.

Confirm with `eas build:list --platform ios --build-profile testflight --limit 1` (status `finished`).

### 4.2 Upload to App Store Connect (TestFlight only)
```bash
pnpm submit:ios:testflight     # = eas submit --platform ios --profile testflight --latest
# or build and upload in one go:
pnpm release:ios:testflight    # = eas build ... --profile testflight --auto-submit
```
- On the first upload, EAS asks for an App Store Connect API key (or Apple ID). If needed, it **creates the app record** with the same bundle identifier.
- After that first upload, add the IDs so later submissions run non-interactively:
  ```jsonc
  // eas.json → submit.testflight.ios
  { "language": "en-US", "ascAppId": "1234567890", "appleTeamId": "AB12CD34EF" }
  ```
- Confirm with `eas submit:list --platform ios --limit 1` (status `finished`). Apple then processes the build (usually 5–30 minutes) until App Store Connect shows **Ready to Test**.

`eas submit` uploads to TestFlight only. It never creates an App Store version or submits for App Review. **Don't** click *Add for Review* on an App Store version in App Store Connect.

### 4.3 Beta information, tester groups and public link
1. Fill in `distribution/testflight.config.json`: feedback email, marketing and privacy URLs, and the Beta App Review contact. The beta app description and *What to Test* text are pre-written. The script refuses to run while any placeholder remains.
2. Export the API key (never commit the `.p8`):
   ```bash
   export ASC_KEY_ID=AB12CD34EF
   export ASC_ISSUER_ID=xxxxxxxx-xxxx-xxxx-xxxx-xxxxxxxxxxxx
   export ASC_KEY_PATH=$HOME/keys/AuthKey_AB12CD34EF.p8
   pnpm testflight:setup
   ```
   This creates or updates the following (it's idempotent, so it's safe to re-run):
   - **Beta app information**: description, feedback email, marketing URL, privacy policy URL
   - **Beta App Review details**: contact name, phone, email, notes; no demo account needed
   - **Internal group "Lumora Internal"**: every new build is available automatically, with feedback on
   - **External group "Lumora Beta"**: public link enabled (500-tester cap, adjustable) and feedback on
3. **Internal testers** (≤100, no review): App Store Connect → Users and Access → invite team members. Then go to TestFlight → *Lumora Internal* → add them.
4. **External testers and public link** (≤10,000, needs Beta App Review):
   ```bash
   pnpm testflight:distribute                         # latest processed build
   pnpm testflight:distribute -- --build 12 --what-to-test "Try the new model picker"
   pnpm testflight:status                             # groups, public link, review state
   ```
   `distribute` sets *What to Test*, adds the build to *Lumora Beta* and submits it for **Beta App Review**. That's TestFlight's external-testing check, not an App Store release. Once Apple approves it (often within a day for the first build, faster afterwards), the public link `https://testflight.apple.com/join/XXXXXXXX` printed by `status` is live. You can also invite people by email under TestFlight → *Lumora Beta* → Testers.

**No-script alternative:** in App Store Connect → your app → TestFlight:
- Fill in **Test Information** (description, feedback email, URLs, review contact).
- Create the **Internal Testing** and **External Testing** groups.
- In the external group, add the build, then enable **Public Link**.

### 4.4 Tester instructions
1. Install **TestFlight** from the App Store.
2. Open the public link or the email invitation on the iPhone, then tap **Accept → Install**.
3. To send feedback, take a screenshot and tap **Share Beta Feedback**, or open TestFlight → Lumora AI → **Send Beta Feedback**. Crash reports are sent automatically. Testers can also email the feedback address in the config.

Requirements: iOS/iPadOS 16.4+ (deployment target generated by Expo SDK 58 prebuild). TestFlight builds expire after **90 days**, so upload a new build before then.

## 5. iOS method B: ad hoc IPA (registered devices only)

### 5.1 Register devices (UDIDs)
```bash
pnpm devices:register          # = eas device:create
```
Choose **Website**. EAS prints a URL and QR code. Each tester:
1. Opens the URL in **Safari** on the iPhone/iPad and downloads the configuration profile.
2. Goes to **Settings → Profile Downloaded → Install** (this only reports the UDID; it doesn't install an app).

The device is then registered in your Apple Developer team. Other options in the same command: **Input** a UDID manually (from Finder/Apple Configurator on a Mac), or import a list. Check with:
```bash
pnpm devices:list              # = eas device:list
```

### 5.2 Build
```bash
pnpm build:ios:adhoc           # = eas build --platform ios --profile ios-adhoc
```
EAS asks which registered devices to include, then creates an **Ad Hoc provisioning profile** for the same bundle identifier (reusing the Distribution certificate) and produces a signed `.ipa`. Confirm with `eas build:list --platform ios --build-profile ios-adhoc --limit 1` (status `finished`).

### 5.3 Install
- **Over the air:** open the EAS build page URL in **Safari on a registered device** and tap **Install**.
- **Via a Mac:** download the `.ipa` from the build page and install it with Apple Configurator 2 or Finder (drag it onto the connected device).

**Device requirements:**
- The device's UDID must have been included in the provisioning profile **when the build was signed**.
- On iOS/iPadOS 16+, **Developer Mode** must be on: Settings → Privacy & Security → Developer Mode → On, then restart and confirm.
- iOS/iPadOS 16.4 or later.
- The ad hoc profile is valid for up to one year (tied to the distribution certificate).

### 5.4 Adding devices later
```bash
pnpm devices:register                     # register the new UDIDs
pnpm resign:ios:adhoc                     # re-sign the latest ad hoc build with an updated profile (no rebuild)
# or rebuild and force a fresh profile:
eas build --platform ios --profile ios-adhoc --refresh-ad-hoc-provisioning-profile
```
Each membership year allows up to 100 devices per type (iPhone, iPad, …). Removing a device frees its slot only at renewal.

**Note:** TestFlight and ad hoc builds share one bundle identifier, so installing one replaces the other on the same device.

## 6. Branding

| Asset | Source | Used for |
| --- | --- | --- |
| `assets/brand/lumora-mark.svg` | **Your uploaded image** (unchanged) | Single source of truth |
| `assets/icon.png` | 1024 px, opaque RGB, white mark on `#060B16` | iOS app icon (and the universal fallback) |
| `assets/adaptive-icon.png` + background `#060B16` | White mark inside the 66/108 dp safe circle | Android adaptive icon |
| `assets/monochrome-icon.png` | Single-colour silhouette | Android 13+ themed icons |
| `assets/splash-icon.png` | White mark, 160 dp wide on `#060B16` | Branded splash screen (both platforms) |
| `assets/brand/lumora-mark-white.png` | Tight crop | In-app header logo and assistant avatar |

The uploaded SVG defines its own colours: `#171717` in light mode and white in dark mode. Lumora is a dark-only app, so the assets use the SVG's **dark-mode variant** (white) on Lumora's midnight navy. To change the colours or sizes, edit `BRAND` / `SPECS` in `scripts/brand-assets.mjs` and run `pnpm brand:assets` (requires `rsvg-convert` and ImageMagick). `expo prebuild` was verified to generate the Android adaptive, round and monochrome launcher icons, the iOS 1024 px App Icon and the splash images from these files.

## 7. CI (optional)

```bash
export EXPO_TOKEN=<expo access token>
eas build --platform android --profile android-apk --non-interactive
eas build --platform ios --profile testflight --non-interactive --auto-submit   # needs ascAppId/appleTeamId in eas.json and an API key in EAS credentials
eas build --platform ios --profile ios-adhoc --non-interactive                  # uses the current registered devices
```
Non-interactive iOS builds need credentials to exist already, so run each profile once interactively first.

## 8. Release checklist

- [ ] Android package `ai.lumora.app` and `CANONICAL_IDS.android` match; choose an iOS bundle identifier before iOS distribution
- [ ] HTTPS backend deployed and production authentication/usage controls configured; the current shared APK token is not sufficient for public distribution
- [ ] `pnpm verify:release && pnpm test:distribution && pnpm test` pass
- [ ] Android: `android-apk` build **finished**; keystore backed up; test install on a phone
- [ ] TestFlight: build **finished**, submission **finished**, App Store Connect shows **Ready to Test**; `testflight:setup` done; internal testers added; `testflight:distribute` sent; Beta App Review **approved**; public link shared
- [ ] Ad hoc: devices registered; `ios-adhoc` build **finished**; Developer Mode enabled on test devices; install verified
- [ ] No App Store version was submitted for review
